# 本机记录器

- 模块定位：跑在你电脑上的小程序。Claude Code、Codex 的钩子每触发一次，它往本机事件日志追加一行；同步时从日志算出「到站的任务」，把已绑定副业的那部分上传。
- 对应代码：`integrations/recorder/`（TypeScript 严格模式；打包成单个文件放进插件）
- 所属里程碑：[M6 编程自动记录](../roadmap.md#m6)
- 总规则与算法：[编程自动记录](编程自动记录.md)；接入方式：[编程记录接入](编程记录接入.md)；服务器一侧：[编程记录接口与显示](编程记录接口与显示.md)
- 当前状态：已完成（2026-10-02 用户验收通过）
- 最近更新：2026-10-02

## 职责与边界

负责：钩子入口（快、静默、永不报错）；认目录名；追加事件日志；发现新提交；从日志算出任务和时间段；上传；本机查询；回填历史。

不负责：钩子怎么配进 Claude Code / Codex（[编程记录接入](编程记录接入.md)）；服务器怎么存（[编程记录接口与显示](编程记录接口与显示.md)）。

## 目录与分层

```
integrations/recorder/
  package.json  tsconfig.json  build.mjs        # build.mjs 用 esbuild 打包成单文件
  src/
    cli.ts                  # 命令入口：解析参数、分发
    commands/               # hook.ts sync.ts status.ts done.ts setup.ts backfill.ts tasks.ts doctor.ts
    core/                   # 纯逻辑，不读文件、不联网、不调 git（全部可单测）
      constants.ts types.ts project-name.ts presence.ts share.ts arrivals.ts titles.ts rounding.ts engine.ts
    store/                  # 本机文件：paths.ts event-log.ts state.ts lock.ts config.ts
    git/                    # git.ts：GitRunner 接口 + 真实实现；resolve-project.ts；commits.ts
    agents/                 # claude-code.ts codex.ts：钩子负载 → 事件；会话文件 → 回填事件
    upload/                 # client.ts（fetch 加超时和重试）build-payload.ts（任务 → 上传请求，分批）
    sync/                   # sync.ts（取绑定 → 算 → 传 → 进行中）live.ts
```

依赖方向：`commands` → `sync`/`agents`/`store`/`git`/`upload` → `core`；`core` 不依赖别的目录。上传请求和响应的类型来自 `src/sync/recorder-protocol.ts`（相对路径引用，记录器、Worker、页面共用）。

构建：`pnpm build:recorder` 用 esbuild 打成 `integrations/claude-code/bin/deverdesk-recorder`（CommonJS，开头 `#!/usr/bin/env node`，目标 Node 18，不压缩），提交进仓库（插件是整个仓库分发的）。一条单测重新打包到临时目录并和提交的文件逐字比较，防止忘了重新打包。

## 本机文件

根目录 `~/.deverdesk/`，环境变量 `DEVERDESK_HOME` 可以改（测试和多账号用）。

| 文件 | 内容 | 写入方式 |
| --- | --- | --- |
| `events/YYYY-MM-DD.jsonl` | 事件日志，一天一个文件（按事件时间的 UTC 日期），每行一个事件 | 只追加，一次 `appendFileSync` 写一整行（行长 ≤ 4 KB） |
| `state.json` | 各仓库最后见到的提交、目录名缓存、各会话第一次见到的时间（`sessionStarts`，最多留最近 1000 个）、各 agent 第一次实时事件的时间、最后一次钩子和同步的结果 | 加锁（最多等 3 秒），写临时文件再改名；改名遇到 EPERM / EBUSY / EACCES（杀毒软件短暂占着文件）最多重试 1 秒，仍失败就记日志放弃，不影响钩子 |
| `uploaded.jsonl` | 已上传的任务键和时间段键，每行一个 | 只追加，只有持有 `sync.lock` 的同步进程写 |
| `bindings.json` | 服务器返回的已绑定目录名（缓存 5 分钟，断网时继续用） | 同步进程写 |
| `config.json` | `{ "url": "…", "token": "dd_…" }`，`setup` 命令写入；文件权限 0600 | `setup` 写 |
| `logs/recorder.log` | 出错记录（超过 256 KB 时留最后一半） | 追加 |
| `sync.lock` | 同一时刻只让一个同步在跑；超过 5 分钟当作残留 | `wx` 方式创建 |
| `locks/<仓库路径哈希>.lock` | 每个仓库一把锁：同一仓库的并发钩子不会重复消费同一批提交；不同仓库互不等待 | `wx` 方式创建，最多等 3 秒，拿不到就跳过这次提交发现（下次钩子补上） |
| `settle-<到期毫秒>.lock`、`settle-schedule` | 延迟同步的预约（同一沉淀时刻附近只留一个等待中的进程）和防死循环的指纹 | 钩子和同步写；预约文件由睡醒的同步进程自己删 |
| `bin/deverdesk-recorder` | `setup --install-codex-hooks` 复制出来的固定位置，Codex 钩子指向它（插件升级后路径不会失效） | `setup` 写 |

事件日志一直留着（一年约十几 MB）。读日志时去重：提交事件按「仓库 + 提交号」，其他事件按（agent、会话、种类、时间）；所以回填和重复追加都安全。多进程同时追加同一个文件，实测（Windows，8 个进程各 400 行、3.5 KB 到 20 KB 的行）没有交错和坏行。

## 事件

```ts
interface EventBase {
  v: 1
  t: number                       // 毫秒时间戳；提交事件取提交自己的时间
  agent: "claude-code" | "codex"
  session: string                 // 会话编号（窗口）；提交事件里是「发现它的那个窗口」，只作参考，归属由引擎按提交时刻谁在场决定
  dir: string                     // 目录名（认项目那一节算出，保留原大小写）；引擎对同一会话一律用它第一个事件的 dir
  cwd: string
  backfill?: true                 // 回填出来的
}
type RecorderEvent =
  | (EventBase & { kind: "start"; source?: string; repo?: string })
  | (EventBase & { kind: "prompt"; text?: string })                 // text：你这句话的第一句，≤ 120 字
  | (EventBase & { kind: "stop"; summary?: string })                // summary：AI 最后一条回复的第一句，≤ 200 字
  | (EventBase & { kind: "end"; reason?: string })
  | (EventBase & { kind: "commit"; repo: string; sha: string; subject: string; body?: string;
                   additions: number; deletions: number; files: number; authoredAt: number })
  | (EventBase & { kind: "done"; title: string })
```

提交说明的 `body` 只留前 500 字，只用来找 `T-123` 这类任务引用，不上传。

## 钩子入口

`deverdesk-recorder hook <agent> <事件名>`：

- Claude Code：从标准输入读钩子的 JSON（字段见 [编程记录接入](编程记录接入.md#钩子负载)）。
- Codex：和 Claude Code 一样，钩子从标准输入读 JSON。
- 全程**不向标准输出写任何东西**（只有 `SessionStart` 在有简报时输出一段 JSON），不向标准错误写；任何异常写进 `logs/recorder.log`，退出码一律 0——记录器永远不能影响 AI 的工作。
- 环境变量 `DEVERDESK_RECORDER_INTERNAL=1` 时直接退出（记录器自己启动的子进程不再触发记录）。
- 读标准输入最多等 3 秒（宿主不关管道时不会挂住），超时按已读到的内容处理；Git 子进程启动失败、工作目录路径过长等一切异常都被兜住（`uncaughtException` / `unhandledRejection` 也静默退出码 0）。
- 钩子耗时和事件日志大小无关：会话第一次见到的时间记在 `state.json` 的 `sessionStarts` 里，只有「该仓库还没有基线又要查提交」时才用到，不再扫描日志。实测 60 MB 日志下 `UserPromptSubmit` p50 约 150 ms，`Stop` 约 290 ms。

每个事件做的事：

| 事件 | 动作 | 耗时目标 |
| --- | --- | --- |
| `SessionStart` | 认目录名（先查缓存；Claude Code 取环境变量 `CLAUDE_PROJECT_DIR`，没有取 `cwd`）、追加 `start`、给这个仓库记下当前 HEAD 作为基线（只有第一次见到这个仓库才记）；目录已绑定且有凭据时输出简报（见下） | 不联网时 ≤ 300 ms；要出简报时联网最多等 0.8 秒，超时就放弃、不出简报；输出后钩子立刻退出（不等连接超时），实测服务器不通时约 1.3 秒 |
| `UserPromptSubmit` | 追加 `prompt`；距上次同步超过 60 秒就在后台启动一次 `sync`（为了更新进行中） | ≤ 150 ms |
| `Stop` | 追加 `stop`；发现新提交并追加 `commit`；后台启动 `sync`（同样 60 秒节流，有新提交时不节流）；有新提交时再启动一个延迟同步（见「同步」） | ≤ 300 ms（实测提交没变 180–190 ms，提交变了约 290 ms） |
| `SessionEnd` | 追加 `end`；发现新提交；后台启动 `sync`（不节流）和延迟同步 | ≤ 300 ms，钩子总共只有 1.5 秒预算 |
| `PostToolUse`（只在 Bash 命令是 `git commit` 时触发） | 发现新提交并追加（让提交尽早入日志，归属仍由引擎决定）；启动延迟同步；不启动普通 `sync` | ≤ 200 ms |

「后台启动」= `spawn(process.execPath, [自己, "sync"], { detached: true, stdio: "ignore", windowsHide: true, env: { ...process.env } }).unref()`（普通同步）或 `[自己, "sync", "--delay", "<毫秒>"]`（延迟同步），同一时刻只有一个 `sync` 在跑（`sync.lock`），所以重复启动无害。实测：钩子启动的分离子进程在 Claude Code 退出后仍能继续运行。

`UserPromptSubmit`、`Stop`、`PostToolUse` 配成后台运行的钩子（不拖慢你）；`SessionStart`、`SessionEnd` 同步。注意实测：在 `claude -p`（非交互）里，如果「干完一轮」钩子设成后台运行，`SessionEnd` 钩子可能不触发（交互会话不受影响）；所以任何逻辑都不能依赖 `end` 一定出现。

### 简报

目录已绑定时，`SessionStart` 输出：

```json
{ "hookSpecificOutput": { "hookEventName": "SessionStart", "additionalContext": "<文字>" } }
```

文字（中文，≤ 1200 字，没有的块不写）：

```
DeverDesk · 副业「模板站」（运营中）
今天计划：T-141 优惠券满减（60m，高）；T-143 写更新日志（30m）
已逾期：T-120 修复订单导出（截止 09-28）
待完成的里程碑：v0.2 发布（截止 10-15）；上线推广（截止 10-31）
其他没做完的：T-150 …；T-151 …（最多 15 条）
发布之后，如果有一个待完成的里程碑明显对得上（名字或版本号吻合），用 manage_project 的 complete_milestone 把它标成完成并告诉用户；对不上或有几个候选，先问用户。
提交说明里写 Closes T-141 之类的编号，这次提交就会把那个任务标成完成；没写编号的提交会自动记成新任务。
```

数据来自 `GET /api/recorder/briefing`，本机缓存 10 分钟；联网失败、没凭据、没绑定都不输出（静默）。「待完成的里程碑」一行放在「其他没做完的」前面（预算紧时先舍后者），最多 8 个，多出的在行末写「（另有 N 项）」；没有待完成的里程碑时这一行和倒数第二行的发布提醒都不出现，最后一行的任务编号提醒永远在。

## 认目录名

`resolveDirName(cwd)`（`git/resolve-project.ts`，git 调用走 `GitRunner` 接口，单测用假的）：

1. 先查 `state.json` 的 cwd 缓存（有效期 1 天）。
2. 用 `git rev-parse` 查事实（每次调用约 33–58 毫秒）：先 `rev-parse --path-format=absolute --git-common-dir --is-bare-repository`（**`--path-format=absolute` 必须写在 `--git-common-dir` 前面**）；不是裸仓库再 `rev-parse --show-toplevel`；公共目录不以 `/.git` 结尾（可能是子模块）时再 `rev-parse --show-superproject-working-tree`。**不要把几个选项合成一次调用后按行号解析**：实测裸仓库和在 `.git` 目录里运行时 `--show-toplevel` 会报错（退出码 128）使整次调用失败，普通仓库不输出超级项目那一行而子模块多输出一行；每次调用单独看退出码和输出。按 [编程自动记录](编程自动记录.md#认项目只看文件夹名) 的表格取名。
3. git 失败（不是仓库、没装 git）：取 `cwd` 最后一段；`cwd` 是盘符根目录或用户主目录时取它的名字（照常记，反正没绑定就不上传）。
4. 路径统一把 `\` 换成 `/` 再取最后一段，WSL 路径、Windows 路径、末尾斜杠都能处理。

纯函数部分（`core/project-name.ts`）：输入 `{ cwd, commonDir?, toplevel?, superproject?, bare? }`，输出目录名，单测覆盖上表每一行。

## 提交怎么发现

`detectNewCommits(git, repoRoot, previous, sessionStartMs)`（`git/commits.ts`）。`state.repos` 以**工作树根目录**（`git rev-parse --show-toplevel`）为键，不同的工作树各记各的 HEAD（派活开的额外工作目录是主场景，用主仓库路径做键会互相覆盖）。每个仓库一把锁（`locks/<仓库路径哈希>.lock`，最多等 3 秒，拿不到就跳过这次，下次钩子补上），读状态、查 git、追加事件、写状态都在这把锁里，两个窗口的钩子同时发现同一批新提交时只有一个能拿走它们；全局 `state.lock` 只包住最后那一下毫秒级的写状态，git 命令不再占着它（评审实测 8 个不同新仓库同时开会话时旧做法有 25% 抛锁超时）。

1. `git -C <repo> rev-parse HEAD`。
2. 和 `state.repos[repo].head` 比：
   - 相同 → 结束。
   - 没有记录且是 `SessionStart` 钩子 → 记下当前 HEAD 作为基线，不产生事件（历史提交由回填负责）。
   - 没有记录且不是 `SessionStart`（会话中途 `git init`，或 AI `cd` 进了一个新仓库）→ 记下基线，同时取这个会话开始时间以后的提交（`--since=<会话开始秒数>`，最多 50 个），免得新项目的第一个提交丢掉。
3. 有记录且不同：`git log --no-merges --format=<记录标记>%H<字段标记>%ct<字段标记>%at<字段标记>%ae<字段标记>%s<字段标记>%B<字段标记> --numstat <旧head>..HEAD`。两种标记是**每次调用随机生成的字符串**（不再用 ``、``，提交说明里有控制字符时旧做法会丢提交或截断），说明为空的提交照常记录。输出超过上限（单个提交改了几十万个文件）或 git 报错时，退一步只取元数据（不带 `--numstat`，行数记 0），并且**一定推进基线**，不会让这个仓库永久卡死。**记录标记放在每条记录的开头**：实测 numstat 的行数列表跟在该提交的信息之后，分隔符放末尾会让每个提交拿到前一个提交的行数。旧 head 已经不在历史里（对象被清掉才会报错退出，仅仅不是祖先时命令是正常的）→ 改用 `--since=<最后一个提交时间的秒数>` 加 `-n 50`。
4. 过滤：作者邮箱和仓库里 `git config user.email` 不一致的丢掉（拉下来别人的提交）；仓库没配邮箱就不过滤；`seen` 里有同样「作者时间|说明」的丢掉（amend 后重复）。
5. 每个剩下的提交追加一个 `commit` 事件（`t` 取提交时间 `%ct × 1000`，改动行数来自 numstat，二进制文件算 0 行 1 个文件；`dir` 是该仓库的目录名），然后更新 `head`、`lastCommitAt`、`seen`（只留最近 200 个）。事件按「仓库 + 提交号」全局去重，哪个窗口先发现无所谓；归属由引擎决定（见 [编程自动记录](编程自动记录.md#提交归属)）。

一个提交只在「一轮超过 15 分钟、期间 `PostToolUse` 没抓到」时才会等到那一轮结束才被发现，此时它的时间早于现在；引擎按提交时刻谁在场来归属，所以不影响正确性，只影响多久之后出现。

## 同步 `sync`

```
sync [--all] [--dry-run] [--days 60] [--delay <毫秒>]
  0. --delay：先睡这么久（最多 20 分钟）再继续；同一时刻附近（±30 秒）已经有一个等待中的就不再启动
  1. 取 sync.lock；取不到就退出
  2. 读凭据（环境变量 → Claude Code 插件选项 → config.json）；没有就退出（记一行日志）
  3. 取 bindings（缓存 5 分钟；联网失败用缓存；没有缓存就退出）；绑定清单和上次不同（新绑了或解绑了目录）时这一轮读全部事件，之后恢复 --days
  4. 读事件日志：最近 --days 天（默认 60，--all 全部）
  5. engine.computeTasks(events, now) → 已沉淀的任务（到站后已过 SETTLE_DELAY）+ 进行中窗口（临时估算）
  6. 挑出要上传的：目录名已绑定，且任务键或时间段键不在 uploaded.jsonl 里
  7. 按 ≤ 10 个任务、≤ 30 条改动分批 POST /api/recorder/upload（任务数 + 时间段数）：
     成功的键写进 uploaded.jsonl（服务器说 duplicate 的也算成功；说 unbound 的不记，可能刚解绑）；
     整个请求 400（形状或上限问题）：把这批拆成一个一个任务重发，只把真正被拒的那个任务记「拒绝」（带原因和记录器版本，下个版本再试）；
     服务器逐任务返回 invalid：只记那个任务；
     401/403/409（任务刚好被你改动）/网络/5xx：停止本轮，留着下次重试
  8. PUT /api/recorder/live：进行中窗口（只含已绑定目录）；和上次相同且距上次不到 60 秒就不发
  9. 如果还有「已到站、没沉淀」的任务：在 (now, now + SETTLE_DELAY] 里二分查找最早能出现新任务的时刻（精度 5 秒），启动一个 --delay 同步；
     （闲置到站的任务是「最后动静 + 2 小时」才出现，不能用「到站时刻 + 沉淀」算，否则会每秒自己拉起自己）
     写 state.lastSync，释放锁
```

`--dry-run` 只打印要传什么，不联网写入。`--days` 之外更早的事件不参与计算；绑定一个很久以前的目录时，第 3 步的「绑定变化」会自动读全部一次。

**延迟同步**：发现新提交（`Stop`、`PostToolUse`）和会话结束时，记录器后台启动 `sync --delay <到沉淀的毫秒数>`，睡到该任务沉淀的时刻（最多 20 分钟）再同步一次，然后退出——不开常驻进程，也不会等到隔夜才有人触发。同一个沉淀时刻附近只留一个等待中的进程（用 `<home>/settle-<到期毫秒>.lock` 判断；预约文件路径通过环境变量 `DEVERDESK_RECORDER_SETTLE_LOCK` 传给睡着的进程，睡醒后由它自己删）。下一次预约离现在不到 5 秒时，用事件的指纹（`settle-schedule`）防止同一批事件反复预约。

**上传细节**：压缩后的时间段键、任务键都不超过 200 字；提交说明截到 200 字；任务编号不在 1–999999 就不带；提交号不是 7–64 位十六进制的提交不带。已经上传过的任务晚些时候又并进了新的时间段（零碎提交），只发还没上传过的时间段。绑定清单要等一轮同步成功之后才写进缓存（失败了下一轮仍会读全部事件）。没有凭据时不改写「最近同步」的结果。

## 回填 `backfill`

只回填「该 agent 第一个实时事件」之前的时间（`state.firstLiveEvent[agent]`；还没有实时事件就回填全部），避免历史数据和实时数据重叠改变平分结果。回填出来的事件带 `backfill: true`，入日志时去重。

### Claude Code

读 `$CLAUDE_CONFIG_DIR/projects`（默认 `~/.claude/projects`）下每个目录里的 `*.jsonl`，跳过 `subagents/` 子目录。逐行流式读（单个文件可达上百 MB），只解析 `"type":"user"` 和 `"type":"assistant"` 的行。实测的结构（本机 191 个文件、415 个含子代理）：

| 取什么 | 规则 |
| --- | --- |
| 时间 | 行里的 `timestamp`（ISO 字符串，带 `Z`） |
| 会话 | `sessionId` |
| 所在文件夹 | 行里的 `cwd`（取最后见到的） |
| 你的发话 `prompt` | `type == "user"`、不是 `isMeta`、不是 `isSidechain`、`message.content` 里没有 `tool_result`，**没有 `forkedFrom` 标记**（分叉会话复制的历史行，时间和父会话逐行相同），**不是压缩摘要**（`isCompactSummary`），并且 `origin.kind == "human"`；没有 `origin` 字段的老记录：文字不以 `<` 开头、不以 `[Request interrupted` 开头 |
| AI 干完一轮 `stop` | `type == "assistant"`、不是 `isSidechain`、没有 `forkedFrom`、`message.stop_reason == "end_turn"`；**同一条 AI 消息会被拆成多行、每行都带结束标记**（实测 2499 行对应 1473 条消息），按 `message.id`（没有就按 `requestId`）去重，取该消息最后一行的时间 |
| 开始 `start` | 每个会话时间最早的一行的时间 |
| 提交 `commit` | 对会话涉及的每个仓库，在 `[最早活动, 最晚活动 + 15 分钟]` 内用 `git log --since --until` 取一次，直接产出 `commit` 事件（`session` 填最可能的会话，仅作参考；归属由引擎按提交时刻谁在场决定）；仓库已经不在磁盘上就没有提交事件 |

目录名：`cwd` 取**会话文件里时间最早的有 `cwd` 的行**（一个会话里 `cwd` 会随 AI 的 `cd` 变，实测 185 个会话里 74 个出现过多个，不能取最后一个）；该路径还在磁盘上就用 git 认；已经不在（用完删掉的工作树），去掉末尾的 `/.claude/worktrees/<名字>` 再取最后一段。

**文件里的时间会倒退**（实测 113 个文件出现过，最大倒退 23.2 小时）：一律先按时间排序再处理；会话文件按行里的 `sessionId` 分会话（`/resume` 沿用同一个编号，分叉才换编号）。排队发话（你在 AI 忙时敲的，约占 5%）用记录里的处理时刻，不去找敲下的时刻。

## 引擎入口（纯函数）

```ts
// core/engine.ts
export interface EngineResult {
  tasks: ComputedTask[]          // 已到站且已沉淀（到站后过了 SETTLE_DELAY）的任务，按到站时间排序；输出后内容不再变
  open: OpenWindow[]             // 进行中的窗口（临时估算）
}
export function computeTasks(events: RecorderEvent[], now: number): EngineResult

export interface ComputedTask {
  key: string                    // 稳定键：见下
  agent: Agent; session: string; dir: string
  source: "commit" | "done" | "idle" | "end"
  title: string
  finishedAt: number
  commits: { sha: string; subject: string }[]
  taskSeq?: number
  entries: { key: string; start: number; end: number; minutes: number }[]   // 整数分钟 ≥ 1
}
export interface OpenWindow { session: string; dir: string; agent: Agent; since: number; minutes: number }
```

键的写法（稳定，重算不变，也不撞）见 [编程自动记录](编程自动记录.md#键)：任务键 `<agent>:<会话>:<标记编号>`（`c:<提交号>` / `d:<时刻>` / `e:<时刻>` / `i:<时刻>`），时间段键 `<任务键>#<段开始毫秒>#<来源标记编号>`；一批连续提交里每个提交各一个任务（各自的提交号）；并进上一个任务的时间段，来源标记编号是被并入的那个标记。

## 关键决策

| 决策 | 理由 |
| --- | --- |
| 单文件 CommonJS 打包 | 插件按目录分发，用户机器上不装依赖；Node 18 以上都能直接跑 |
| 钩子只追加事件，计算全在 `sync` | 钩子要快；日志只追加所以算多少次结果都一样，规则改了可以重算 |
| 没提交又没结束的工作到下一次钩子触发时才收成任务 | 闲置到站要 2 小时没动静；这类工作本来就没有「完成」的时刻，晚一点出现没有损失 |
| 进行中的窗口由服务器 5 分钟过期，不靠记录器清 | 记录器没有常驻进程，窗口关掉后没人去清 |
| 凭据优先读环境变量里的插件选项 | 令牌存在 Claude Code 的安全存储里，不落盘；Codex 和命令行用 `config.json`（Windows 上没有文件权限保护） |
| 事件日志按 UTC 日期分文件 | 文件名不受时区影响；计算时不看文件边界 |
| 回填只填第一个实时事件之前 | 避免历史会话和实时会话互相平分后改变已上传的数字 |
| 提交归属由引擎决定，事件按「仓库 + 提交号」去重 | 两个窗口同时在一个仓库里干活时，谁的钩子先发现提交是随机的；按提交时刻谁在场归属才是确定的 |
| 延迟同步，不开常驻进程 | 沉淀要等 15 分钟，但不能等到下一次有人触发钩子（可能隔夜）；睡着的进程最多 20 分钟，用完就退出 |
| `done` 命令只写本机日志 | AI 在 Bash 里拿不到插件选项里的令牌；上传由钩子启动的同步完成 |

## 当前实现

`integrations/recorder/` 已按上面的分层完整实现（TypeScript 严格模式，三套 `tsc` 都通过）：

- `core/`：纯函数引擎。`dedupe`（校验、去重、排序，缺必填字段的事件丢弃不抛错）→ `presence`（在场区间）→ `share`（并行平分）→ `attribution`（提交归属，按提交时刻谁在场）→ `arrivals`（到站标记、沉淀、零碎并入、闲置判断，归给窗口的提交也算窗口的动静）→ `titles`、`rounding`（最大余数法，留 1e-9 余量）→ `engine.ts` 编排；`project-name.ts` 从 git 事实算目录名。20,000 个事件、50 个窗口约 170 毫秒。
- `store/`：路径、事件日志（追加永不抛错，行太长先截 text / summary / body / subject / title）、状态（带界的锁等待、改名重试）、锁、配置、隐私开关（`DEVERDESK_NO_PROMPT_TEXT` 和 `config.json` 的 `privacy.promptText`，钩子和回填共用）。
- `git/`：运行器（所有 spawn 错误变成失败结果）、认目录名（含裸仓库、工作树、子模块、`--separate-git-dir`）、提交发现（每个仓库一把锁、随机分隔标记、超大提交退回只取元数据并推进基线）。
- `agents/`：Claude Code 和 Codex 的钩子负载解析；两者的历史回填（Claude Code 会话文件流式读取，按文档里的规则过滤分叉复制行、压缩摘要、子代理）。
- `commands/`：`hook`、`sync`、`status`、`done`、`tasks`、`setup`、`doctor`、`backfill`；`sync/`：同步（含二分算下一次延迟同步的时刻）、进行中上报、简报（`node:http` 请求，超时直接销毁套接字）、后台启动（工作目录放到记录器家目录）；`upload/`：客户端（超时、重试）和请求构建（分批、压缩超长时间段、字段规整到服务器限制）。
- 构建：`build.mjs` 用 esbuild 打成 `integrations/claude-code/bin/deverdesk-recorder`（约 157 KB）。
- 隐藏的测试参数：`sync --now <毫秒>` 把「现在」设成指定时刻（越过沉淀）；环境变量 `DEVERDESK_NO_DELAYED_SYNC=1` 关掉延迟同步（见 [编程记录接入](编程记录接入.md#已知限制)）。
- 版本号 `0.1.1` 写在 `src/version.ts`（命令行 `--version`、上传请求里的客户端版本、请求头 User-Agent、被拒任务的重试判断都用它）和插件清单 `plugin.json` 里各一份，`integrations/claude-code/plugin.test.ts` 有一条单测核对两处一致。Claude Code 靠清单里的版本号判断插件有没有更新，所以改了记录器或插件内容要一起升版本号（被拒绝的任务按「版本号 + 原因」记在 `uploaded.jsonl` 里，升级后会重试）。

## 验证方式

- `pnpm test`：`core/` 每个文件的单测（设计文档里的例子、并行平分、闲置、零碎提交、任务引用、键稳定）加性质测试（取任一中间时刻，已沉淀的任务在更晚的时刻重算后内容不变；时间守恒；输入乱序和重复事件结果一样）；`agents/` 用真实负载样本；`git/` 用假的 `GitRunner` 和真实临时仓库（普通、子文件夹、工作树、子模块、裸仓库、非 git）；`store/` 并发追加和锁；`sync/`、`upload/` 用假客户端。
- 引擎差分测试：另一位评审只按规格文字独立写了一份参考实现，用随机事件流比对：修复后在 9,988 次比对里没有不一致（规格字面读法），剩下只有「内容不同键相同的重复事件取哪条」这一处规格歧义的读法差别。
- 真实回放（只读）：对本机 188 个真实会话做回填预演和写入，发话 1190、干完一轮 1384、开始 188、提交 723，与评审独立重数完全一致；最长一行 1.36 MB，整个回填约 40 秒、峰值内存 225 MB。
- 黑盒压测（评审，16 类问题，已全部修复并各有测试）：钩子耗时随日志变大、服务器不通时的钩子耗时、并发锁、超长路径崩溃、提交说明含控制字符、状态文件被占用、超大提交卡死、闲置到站的自拉起循环、超过 20 段的任务上传失败、超长说明被拒、回填无视隐私开关、绑定变化后补传、`setup` 误删别人的钩子等。
- 退出压测：9 个场景各 40 次（钩子、同步、状态、自检），共 360 次运行全部退出码正确、标准错误为空。
- 端到端：见 [编程记录接入](编程记录接入.md#当前实现)，`pnpm e2e:recorder` 53 项全过。
