# 存储层

- 模块定位：数据仓库和「数据存在哪」之间的一层。页面和数据仓库只管改数据，存到浏览器还是云端由这一层决定。
- 对应代码：`src/state/storage/`（`types.ts` 接口、`local.ts` 浏览器存储、`cloud.ts` 云端存储、`records.ts` 按条找改动和合并、`index.ts` 按版本选用），调用方是 `src/state/store.ts`
- 所属里程碑：[M1 本地版 / 在线版切换](../roadmap.md#m1)（云端存储属于 [M2](../roadmap.md#m2)，细节见 [同步](同步.md)）
- 当前状态：已完成
- 最近更新：2026-09-30

## 职责与边界

负责：启动时读出这台设备上保存的数据；每次修改后保存，并告诉数据仓库有没有存上；在线版还负责把云端拉来的数据交回数据仓库。
不负责：数据怎么改（数据仓库的各个操作）、界面上的保存失败提示（外框的保存反馈）、样例数据生成。

## 结构与数据流

```
页面操作 → 数据仓库的操作（新建任务、记一笔……）
              │ 算出改之后的完整数据(next)
              ▼
        存储层 save(next) ──→ 返回这台设备上有没有存上
              │
              ├─ 本地存储：整份写进浏览器（键 deverdesk:data，格式版本 1）
              └─ 云端存储：和自己记着的上一份比，找出改了哪几条记录排队上传，再写浏览器缓存
                    │
                    └─ 云端拉来别的设备的改动 → 经 connect 登记的通道整份交回数据仓库
```

启动时数据仓库调用 `load()`：
- 本地版：读到就用；读不到（第一次用、格式版本对不上）就生成样例数据。没改过的样例数据隔天打开会按新的一天重新生成。
- 在线版：用这台设备上的缓存；没有缓存就从空白数据起步，等登录后从云端拉取。

## 关键决策

| 决策 | 理由 |
| --- | --- |
| 接口只有 `load` / `save` 两个同步方法，外加在线版用的 `connect` | 在线版也先写浏览器缓存，保存结果当场就知道；上传云端在后台进行，另有同步状态；云端来的数据经 `connect` 登记的通道交回 |
| `save` 只收改之后的完整数据，在线版自己记着上一份 | 数据仓库的修改都是「没改的记录保持原对象、改了的换新对象」，按对象是否相同就能找出改动的记录；由存储层自己记上一份，保存失败后重试也不会漏传改动 |
| 在线版交给数据仓库的起步数据和自己记的上一份是同一个对象 | 两边从同一份开始按对象比较，没动过的记录（比如默认作息设置）不会被当成改动传上去 |
| 本地存储保留 `?fail=save` 演示开关 | 地址栏加上它，第一次保存会故意失败，用来检查失败提示和重试 |

## 当前实现

- `createStorage()`：本地版返回本地存储，在线版返回云端存储。
- 保存失败时数据仓库保留内存里的修改，失败次数加一，外框弹出「没能保存到本机」并给出重试。
- 云端存储的上传、拉取、合并、同步状态见 [同步](同步.md)。

## 验证方式

- `pnpm build:local && pnpm probe`：快速添加后刷新仍在、回顾笔记刷新后仍在。
- 地址加 `?fail=save` 做一次修改，出现保存失败提示，点重试后提示已保存。
- `pnpm test`：`records.test.ts` 覆盖按条找改动和合并。
- `pnpm build && pnpm e2e`：在线版两台模拟设备的同步。
